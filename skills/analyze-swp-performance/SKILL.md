# Analyze Windows sign-in and application performance

Work from the supplied case. Derive customer, host, account, time zone, Windows build, agent build, collector revision, scenario and reproduction times from its evidence. Use earlier reports only for layout. Keep each customer’s evidence, findings and exports in a separate case directory.

## Receive and scope the evidence

1. Preserve the original archives. Verify the full AllEvidence ZIP against its supplied SHA-256 with Get-FileHash or an equivalent. For a mismatch, request the matching pair before relying on the archive. For a missing checksum, record the locally computed hash and mark transfer verification pending.
2. Inventory the ZIP before extracting a working copy. Windows ZIP entries may use backslashes. For lookup on macOS or Linux, normalize both separators and retain the original member name for reads and citations. Read Evidence-assessment.json, the latest Packaging-summary, File-inventory.csv and operator notes. Check actual files and time coverage independently of the collector’s success label. Older kits can have different paths or lack assessments. Locate equivalent raw artifacts and record which checks are possible.
3. If only a native diagnostic or metrics ZIP arrived, analyze the available agent data, state its time window, and identify the additional evidence needed for each unanswered question. Keep different hosts, boots, retries, collection passes and later diagnostics distinguishable.

For an optional Procmon repeat, read `Procmon/Operator-notes.json`, `Procmon/SignIn-milestones.json`, `Trend/PassB-Timed-scans.csv` and `PassBSignInScans` together. Verify the saved PML segments against `Procmon/PassB-segments.csv`. Compare `Events/Channel-exports.csv` for A and `Events/PassB/Channel-exports.csv` for B. Report timing coverage and scan totals separately for each reproduction.

## Ask the operator which Windows machine to use

The computer named in the handoff is the source of the evidence. For each investigation, use the machine and access details the operator has supplied for this case. A hostname in a trace or a connection used for an earlier case does not establish access for this one. Ask only for details still needed.

- **WPR trace analysis.** Ask “Which Windows machine with Windows Performance Analyzer (WPA) or xperf should I use for this ETL? How should I access it, and which case folder is approved for the trace and exports?” If the operator runs the tools, ask them to return the trace statistics and process/file I/O exports for the sign-in or application interval. For xperf reports use the [repository export helper](https://github.com/penica-TrendAI/swp-windows-performance-toolkit/tree/main/Analysis).
- **Live reproduction.** When a finding needs a live test, ask “Which test VM may I use, how should I connect, and which test actions are approved?” Confirm the scope of any reboot, sign-in capture or configuration change before performing it. Identify VM observations separately from findings in the customer trace. One machine can serve both roles if the operator designates it for both.

Connect using the agreed method and transfer case files only to the location approved by the operator. Request a connection alias or account name as needed and keep passwords and private keys out of chat. While waiting for access or exports, continue analyzing the supplied logs, metrics and event records. Record which conclusions still depend on the ETL or a lab test.

## Correlate timing and test attribution

1. **Establish the reproduction window.** Use the pass state in `Cleanup`. For Pass A, start at `RecordedBootUtc` for a reboot or `ArmedAtUtc` for same-boot sign-out/sign-in and end at `TraceStopRequestedAtUtc`. For Pass B, inspect `ReproductionEndUtc` and its source. A finish or recovery timestamp is an upper bound if the actual milestone is unknown. Record the sign-in route (automatic, usual immediate, delayed at the credential screen, or same-boot) when known. Normalize joins to UTC using the captured time zone. Report local time with its offset.
2. **Locate the symptom within that window.** Use `SessionCorroborated`, the affected account, authentication and Explorer times to identify the Windows session. Linked 4624 records can belong to one administrator sign-in. Measure credential submission to usable desktop and application launch to ready only when their milestones are available. Record a deliberate credential-screen hold separately. The GUI launch record in `Cleanup` timestamps the collector opening. Keep it separate from Explorer startup and operator-reported readiness.
3. **Recount scan records inside each interval.** `CapturedPairs`, `AfterSignInPairs` and the timed-scans CSV can include up to five minutes of records after the reproduction end in the current collector. Filter both `StartLocal` and `EndLocal` against the actual boundaries before ranking files. Partition at authentication, Explorer and reproduction end. Keep boundary-crossing pairs separate and identify post-stop activity explicitly. Use the minimum start and maximum completion from the rows when stating the observed span.
4. **Report scan starts and timings separately.** `>>> SCANFILE:` identifies an observed path. Pair it with the matching `<<< SCANFILE:` completion by process/thread and sequence. Use the engine's microsecond field (decimal or hexadecimal) and divide by 1,000 for milliseconds. Preserve sequences across rotations and deduplicate overlapping copies while retaining genuine repeated scans. Count observed starts, distinct paths, and pairs wholly inside the interval separately. Read `Trend/<pass>-SignIn-scan-starts.csv` when available. Older handoffs can omit it or its assessment fields. Use the raw early, live and final AMSP generations and, if needed, those inside the native ZIP. Read `StartUtc.txt` and `Result.json` in the per-pass live AMSP folder. The watcher can start late and copy earlier rotations. Verify coverage from timestamps on scan markers in the files themselves.
5. **Measure metrics coverage independently.** Check `MetricsByPass`, `SamplesDuringReproduction`, the first and last embedded timestamps, the median interval and the largest gap. Recount unique sample times for the narrower sign-in and application intervals. A verified batch with a five-second cadence can contain zero samples during the symptom. In that case agent utilization during the interval is unknown.
6. **State what the interval supports.** For each source show the bounds, observed counts, missing endpoints and gaps. Report zero *observed* starts or pairs for a corroborated window with readable records. Mark counts unknown when boundaries or inputs are missing. A blank operator timestamp leaves that user-experience measurement unknown. Explain which question each evidence gap affects. A missing optional login task or policy export is not evidence of a delay. General agent messages in `ds_agent*.log` can establish agent activity during sign-in even when detailed AMSP timings are unavailable.

For each path, report observed timed count, maximum and summed engine milliseconds **per interval**. Label starts without completions as untimed and keep their durations blank. Keep summary-only paths in the table with blank cumulative time. The native Top 10 count and last scan duration cannot be multiplied to infer total cost. A summary emission time cannot place its listed scans inside sign-in. Identify files generated by the collector, WPR or diagnostic tooling as possible measurement overhead and keep them visible separately from the user's workload.

Use WPR or Procmon file I/O to identify competing activity and, when available, the requesting thread and its wait. An I/O event alone cannot confirm an AMSP scan. Overlapping engine durations can add up to more than elapsed time. Propose a narrow exclusion trial only where symptom-window evidence shows material cost. Configuration XML may contain only list names. Verify the effective scan configuration and inherited exclusion-list members with the policy owner. Document the target, risk, rollback and success criterion. Compare the same account, sign-in route, credential-screen delay, application and readiness milestone on each run.

## Produce and verify the customer report

Deliver matching Markdown and Word reports plus supporting CSVs. Lead with the observed delay, the best-supported explanation and any gap that affects the decision. Include case scope, capture quality, a timeline, findings for sign-in and each application, competing explanations, and prioritized next steps. Tie each material finding to an artifact, time range, metric and unit. Distinguish observed activity, suspected contribution and effects demonstrated by a controlled repeat.

Supply CSVs for interval coverage, the event and process timeline, deduplicated individual scans, and per-file totals including summary-only paths. Include process resource summaries or trial candidates when the evidence supports them. For a partial handoff, supply the tables the available sources support and name the smallest additional capture or export needed.

Before delivery, reconcile report values against the CSVs, confirm units and coverage labels, inspect the rendered Word tables, and check that names, paths, findings and recommendations all belong to the current customer.
